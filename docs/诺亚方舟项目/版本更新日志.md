## v1.0.49 (2026-05-15)

### 🛡️ 修复：识别期间 IAMS 凭证消息丢弃

#### 问题背景
单眼虹膜无法下发（singleIrisAllowed=0），IAMS 快速连发 passport-add。每次失败后都会重新锁定设备。如果此时用户正在进行虹膜认证识别，设备会被 passport-add 的锁定指令打断，识别倒计时不满就锁定。

#### 修复方案
`handleMessage` 入口处增加拦截：当设备处于 `unlocked` 状态（识别进行中）时，丢弃所有 `passport-add`/`passport-update`/`passport-del` 消息，不入队、不记录、不响应。IAMS 会持续重试，识别完成后设备重新 locked，后续消息正常处理。

#### 核心改动

1. **`lib/mqtt-client.ts`**：
   - 导入 `getIrisDeviceLockState` 函数
   - `handleMessage` 中 deviceId 校验后，新增 unlocked 状态检查
   - `isCredentialOp && getIrisDeviceLockState() === 'unlocked'` → 丢弃并打印日志

2. **`lib/device-sync.ts`**：
   - `singleIrisAllowed` 全部改为 `1`（3 处：`syncToIrisDeviceWithoutLock`、`uploadIrisToDevice`、硬编码值）

3. **`lib/db-credentials.ts`**：
   - `LIGHT_COLUMNS` 加入 `content` 字段：密码(type=5)/胁迫码(type=9)的 content 是短文本，虹膜 content 已清理为 null

4. **`tsconfig.json`**：
   - exclude 新增 `electron/release`、`electron/dist`、`scripts`，避免构建时扫描旧代码副本

5. **`lib/mqtt-client.ts`**：
   - `recordMqttEvent` 的 credentialType fallback 查询扩展到所有操作（原仅 passport-del/update）

## v1.0.48 (已发布)

### 🔒 新增：凭证有效期校验

#### 需求背景
IAMS 下发的凭证带有 `startTime` 和 `endTime` 有效期字段（毫秒时间戳）。用户输入用户编码后，需要判断凭证是否在有效期内，未生效或失效的凭证应拦截用户继续操作，提示"用户没有有效凭证"。

#### 核心改动

1. **数据库迁移（`lib/database.ts`）**：
   - `credentials` 表新增 `start_time BIGINT` 列（有效期开始时间戳）
   - `credentials` 表新增 `end_time BIGINT` 列（有效期结束时间戳）

2. **凭证模型扩展（`lib/db-credentials.ts`）**：
   - `Credential` 接口新增 `start_time: number | null`、`end_time: number | null`
   - `upsertCredential` 参数和 SQL 新增 `start_time`、`end_time` 字段
   - `LIGHT_COLUMNS` 新增两列
   - `rowToCredential` 新增映射

3. **passport-add / passport-update 处理（`lib/mqtt-client.ts`）**：
   - 接收 IAMS 的 `data.startTime` → 存入 `start_time`
   - 接收 IAMS 的 `data.endTime` → 存入 `end_time`

4. **有效期校验逻辑（`lib/db-credentials.ts` 新增 `isCredentialValid` 函数）**：
   - `start_time` 为空或 `end_time` 为空 → 判定为"未生效"
   - 当前时间不在 `[start_time, end_time]` 范围内 → 判定为"失效"
   - 返回校验结果 + 提示信息

5. **验证入口拦截（`app/api/auth/verify-password/route.ts`）**：
   - 密码验证：获取用户凭证后 → 调用 `isCredentialValid` 校验 → 失败返回 403 + "用户没有有效凭证"

6. **前端凭证详情页显示（`app/dashboard/credentials/page.tsx`）**：
   - `Credential` 接口新增 `start_time`、`end_time` 字段
   - 详情模态框新增"有效期开始"和"有效期结束"两行，显示格式化时间或"-"

7. **`updateCredentialAttributes` 扩展（`lib/db-credentials.ts`）**：
   - 支持更新 `start_time`、`end_time` 字段（用于 passport-update）

## v1.0.44 (2026-05-13)

### 🐛 attr-set 控制台弹窗问题深度修复

现场环境 IAMS 下发 `attr-set`（含 `deviceTime`）时，每次 PowerShell `Set-Date` 因无管理员权限失败都会弹出一个空白控制台窗口，约 10 秒一次，严重影响用户体验。

**根因分析**：
1. Windows 上 `child_process.execSync` 调用 `powershell.exe` 时默认会弹出新控制台窗口
2. `stdio: 'pipe'` 不足以阻止窗口弹出
3. `publishUpstream` 发送异常时未被捕获，导致 IAMS 收不到响应而重试

**修复方案**：
1. `execSync` 添加 `windowsHide: true` + PowerShell `-WindowStyle Hidden` 双重保险
2. `publishUpstream` 包在 try/catch 中，确保无论发生什么都不会抛出异常
3. 所有内部日志静默处理，减少日志噪音

## v1.0.41 (待发布)

### 🔧 虹膜设备通信稳定性修复

#### 问题现象
虹膜设备下发过程中间歇性出现 `errorCode=97`（App未初始化成功）和 `请求超时` 错误。

#### 根因分析
- `errorCode=97`：并非"已锁定"，而是因使用 `fetch` 导致设备重新初始化。Node.js `fetch()` 复用 keep-alive TCP 连接，虹膜设备的嵌入式 HTTP 服务器不支持连接复用，收到复用连接的请求时会触发设备重新 init
- `请求超时`：同上，keep-alive 连接复用导致请求卡死

#### 修复方案
所有虹膜设备写接口（lock/unlock、memberSave、memberDelete、members）统一使用 Node.js `http.request` 创建独立 TCP 连接，彻底消除 keep-alive 问题。

| 文件 | 修改内容 |
|------|----------|
| `lib/device-sync.ts` | `getIrisDeviceMembers` 改用 `httpRequest`；`checkDeviceStatus` 虹膜分支改用 `httpRequest` |

### 🔧 虹膜设备稳定性深度修复

#### 根因分析：设备崩溃（socket hang up）
IAMS 快速连发同一条凭证时，多条请求逐条入队执行。虽然 `handlePassportAdd` 有"凭证已存在"检查能跳过后续重复请求，但如果 credentialId 不同但 personId 相同的多条虹膜凭证，仍会逐条往设备上传。

**设备崩溃原因判断**：
- memberSave payload 约 822KB（两张 308KB BMP 转 base64 各 411KB + JSON 开销）
- 设备嵌入式 HTTP 服务器在处理大 payload 时有一定概率内存溢出崩溃
- 崩溃后设备自动重启，期间所有请求返回 errorCode=97 或 socket hang up
- 第一次下发成功、第二次崩溃说明是间歇性问题，不是 payload 本身的硬伤

#### 修复方案
1. **所有虹膜设备接口改用 `http.request`**：彻底消除 Node.js `fetch()` keep-alive 连接复用问题
2. **指令间隔从 300ms 加到 1000ms**：所有发往虹膜设备的指令通过 `irisCommandGuard()` 统一控制，间隔 ≥1 秒
3. **锁定→上传等待从 200ms 加到 1000ms**：给设备更多时间消化锁定指令
4. **memberSave 自动重试**：socket hang up 或 errorCode=97 时，等 15 秒设备重启后重试，最多 2 次
5. **personId 10 秒去重锁**：`syncToIrisDevice` 执行期间，同一个 personId 的其他请求直接跳过，10 秒自动清除
6. **轮巡器忙碌跳过**：`irisDeviceState === 'busy'` 时整轮轮巡跳过，不发任何请求到设备
7. **httpRequest 加 `Connection: close` 头**：明确告诉设备请求完成后关闭连接

#### 不要重蹈的覆辙（重要判断记录）
- **永远不要用 `fetch` 访问虹膜设备**：keep-alive 连接复用会导致设备重新初始化（errorCode=97）
- **任何情况下发往虹膜设备的指令间隔不能少于 1 秒**：包括 memberSave、memberDelete、members、memberSaveState
- **IAMS 快速连发同一条凭证**：personId 去重锁 + 凭证已存在检查双重保护
- **设备崩溃后不要立即重试**：等设备重启完成（约 10-15 秒）再重试
- **不要在 memberSave 期间有任何其他请求到达设备**：轮巡器忙碌检查、personId 锁、指令间隔三重保护

## v1.0.40 (2026-05-08)

### 🔒 虹膜数据按需下发（本地加密存储 + 临时上传）

#### 问题背景
虹膜设备里存了所有人的数据，任何人站在设备前都能识别，影响使用体验。

#### 解决方案
虹膜设备平时保持锁定状态、不保留人员数据。仅在用户身份编码验证通过后、需要虹膜认证时，临时上传该人员的虹膜数据到设备，识别完成后立即删除并重新锁定。

#### 核心流程

**IAMS 下发虹膜凭证（passport-add）**：
1. 正常上传到虹膜设备验证（锁定→等待8秒→memberSave→解锁）
2. 上传成功 → AES 加密存储到 `data/iris_data/<credentialId>.json.enc` → 数据库 `iris_data_path` 字段记录文件路径 → 调用 `/memberDelete` 从设备删除数据 → 保持锁定状态 → 返回 IAMS 成功
3. 上传失败 → 不存文件不删设备 → 照常返回 IAMS 失败

**用户认证时（虹膜步骤）**：
1. 前端调 `/api/device/iris/preload` → 后端读加密文件 → 解密 → 直接 memberSave 上传（设备已锁定，无需额外锁定）→ 解锁 → 启动 180 秒安全计时器
2. 前端收到成功 → 启动虹膜轮询
3. 识别成功/超时/失败 → 调 `/api/device/iris/cleanup` 删除设备数据 + 重新锁定
4. 回到首页 → 兜底 cleanup（万无一失）

**凭证删除（passport-del）**：
- 删除数据库凭证 + 删除本地加密文件（设备上已无数据，无需调用删除接口）

## v1.0.39 (2026-05-06)

### 🔧 虹膜上传等待 8 秒问题修复

#### 问题现象
`syncToIrisDevice` 执行完整流程时（锁定 → memberSave → 解锁），锁定成功后必须等待 8 秒再执行 memberSave 上传，否则上传会失败。

#### 根因
Node.js 的 `fetch()` API 默认启用 HTTP/1.1 keep-alive，同一目标地址的多个请求会**复用同一条 TCP 连接**。虹膜设备的嵌入式 HTTP 服务端**不支持 keep-alive 连接复用**，在同一连接上连续收到锁定和上传请求时设备无法正确处理。

8 秒等待恰好让 Node.js 的 keep-alive 连接超时断开，后续请求走了新 TCP 连接才成功。而 Postman 三个窗口各用独立 TCP 连接，不存在此问题。

#### 解决方案
新增 `test-iris-upload` API 使用 Node.js 原生 `http.request` 替代 `fetch`，每条请求创建独立 TCP 连接，锁定后等待从 8 秒缩短到 300ms 即可成功上传。

#### 新增功能
- **新增按钮**：系统设置页面"设备工具"区新增「虹膜测试上传」和「锁定虹膜设备」按钮，方便现场调试虹膜设备
- **自动保存 payload**：每次虹膜下发时自动将实际发送的完整 BMP payload 保存到 `data/iris_last_request.json`，方便 Postman 对照测试

## v1.0.23 (2026-04-18)

### 🐛 致命问题修复

#### 1. 组合认证通行记录从未上传到 IAMS

**问题描述**：组合认证成功后，通行记录从未写入数据库，也从未上报给 IAMS 服务器。

**根因**：
- 组合认证页面从 `/api/auth/types` 接口获取 `credentialId`
- 该接口**从未返回过 `credentialId` 字段**
- 页面用 `|| 0` 兜底，`credentialId` 始终为 0
- 上传 API 中 `!credentialId` 验证：`!0 === true` → 直接返回 400 拒绝

**修复内容**：
| 文件 | 修改 |
|------|------|
| `lib/database.ts` | `findByUserCode` SQL 查询增加 `credential_id` 字段 |
| `app/api/auth/types/route.ts` | API 响应新增 `credentialId` 字段 |
| `app/api/pass-log/upload/route.ts` | 验证改为 `credentialId === undefined \|\| === null`，允许值为 0 |
| `app/kiosk/combined/page.tsx` | 无条件设置 `userInfo`（不依赖 `personName` 是否有值） |

#### 2. 组合认证步骤判断不准确（闭包问题）

**问题描述**：3 凭证组合认证时，有时第一步验证完就通过了，有时第二步完就通过了，有时三步全完成才通过——行为不可预测。

**根因**：
- `handleBiometricComplete` 的 `useCallback` 依赖 `[steps, goToSuccess]`
- 该函数被 `startIrisPolling` 和 `startPalmPolling` 内联调用
- polling 函数的依赖数组是 `[identityId, countdown, stopPolling]`，**不包含 `handleBiometricComplete`**
- polling 函数中引用的 `handleBiometricComplete` 是创建时的旧闭包版本，其中读取的 `steps` 可能是空数组 `[]`
- `steps.indexOf(step)` 返回 `-1`，导致错误判断下一步或直接 `goToSuccess()`

**修复内容**：
| 文件 | 修改 |
|------|------|
| `app/kiosk/combined/page.tsx` | 新增 `stepsRef` 追踪最新 `steps`；新增 `goToSuccessRef` 追踪最新 `goToSuccess`；`handleBiometricComplete` 改为空依赖 `[]`，内部通过 ref 读取最新值 |

### 🔧 其他修复

- **组合认证日志路径调整**：从 `data/组合认证日志.log` 改为 `logs/combined-auth.log`，与 `startup.log`、`nextjs.log` 放在同一目录下（`%APPDATA%\noah-ark-electron\logs\`）
- **组合认证密码/胁迫码逻辑**：`hasPasswordType` 改为只判断 `includes(5)`，不再错误地将只有胁迫码(9)的情况当作需要密码

- **组合认证掌纹识别**：请求代码统一为字符串 `'103'`/`'102'`，`code` 比较改为 `String()` 转换，与单独认证掌纹完全一致
